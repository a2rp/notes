# 127 - EventEmitter, signals, timers, and the Node.js event loop: Q&A

Review event listeners, timer behavior, event-loop scheduling, and process shutdown. Each answer appears immediately after its question.

## Multiple-choice questions

### 1. When does EventEmitter call listeners registered with on()?

- A. Synchronously during emit(), in registration order
- B. Only after a timer completes
- C. In a separate worker thread
- D. Only when the process exits

**Answer: A.**

**Explanation:** emit() invokes the current listeners synchronously. A listener can explicitly schedule later work, but emitting an event does not do that automatically.

### 2. What is the difference between on() and once()?

- A. on() runs on every emission; once() removes its listener after one emission
- B. on() is synchronous; once() is always asynchronous
- C. on() handles errors; once() cannot
- D. There is no difference

**Answer: A.**

**Explanation:** once() is useful for one-time events such as ready or completed.

### 3. What happens if an EventEmitter emits error without an error listener?

- A. Node.js throws the error
- B. The event is silently ignored
- C. Node.js retries the operation
- D. The emitter converts it to a warning

**Answer: A.**

**Explanation:** error is a special EventEmitter event. An unhandled error can terminate the process.

### 4. Does EventEmitter automatically await a Promise returned by an async listener?

- A. No
- B. Yes, before calling the next listener
- C. Only if the event name is error
- D. Only when using once()

**Answer: A.**

**Explanation:** A rejected Promise from an async listener can become unhandled unless the listener handles it or the emitter is deliberately configured for rejection capture.

### 5. What does a setTimeout() delay represent?

- A. A threshold after which the callback may run
- B. An exact appointment time
- C. A maximum duration for the whole process
- D. A promise that no other callback will run first

**Answer: A.**

**Explanation:** Event-loop work and operating-system scheduling can make the callback run later than the requested delay.

### 6. Which event-loop phase runs setImmediate() callbacks?

- A. Check
- B. Poll
- C. Timers
- D. Close

**Answer: A.**

**Explanation:** The check phase follows poll processing. This is why setImmediate() has a useful relationship to callbacks scheduled from I/O.

### 7. At the top level, which always runs first: setTimeout(callback, 0) or setImmediate(callback)?

- A. Neither order is guaranteed
- B. setTimeout() always runs first
- C. setImmediate() always runs first
- D. They always run at the same time

**Answer: A.**

**Explanation:** The order depends on event-loop timing and context. Do not use it as a synchronization contract.

### 8. Is process.nextTick() one of the event-loop phases?

- A. No
- B. Yes, it is the first phase
- C. Yes, it is the poll phase
- D. Yes, it replaces the timers phase

**Answer: A.**

**Explanation:** It uses a special queue processed after the current operation and before the event loop continues.

### 9. What can recursive process.nextTick() scheduling do?

- A. Keep the nextTick queue busy and delay I/O callbacks
- B. Move work to a worker thread
- C. Cancel all timers
- D. Make EventEmitter asynchronous

**Answer: A.**

**Explanation:** If the queue is continuously refilled, Node.js may not get a chance to progress through the event loop.

### 10. What does timer.unref() mean?

- A. The timer alone will not keep the event loop alive
- B. The timer becomes more accurate
- C. The timer runs in a worker
- D. The timer cannot be cancelled

**Answer: A.**

**Explanation:** The process may exit before the timer callback runs if nothing else keeps the event loop active.

### 11. Which signal is commonly generated by pressing Ctrl+C in a terminal?

- A. SIGINT
- B. SIGKILL
- C. SIGSTOP
- D. SIGPIPE

**Answer: A.**

**Explanation:** SIGINT from the terminal is widely supported and commonly represents an interrupt request.

### 12. Can a Node.js process install a listener for SIGKILL and clean up before exit?

- A. No
- B. Yes, if the handler is once()
- C. Yes, on Windows only
- D. Yes, if process.exitCode is zero

**Answer: A.**

**Explanation:** SIGKILL cannot be caught. Graceful cleanup requires a catchable shutdown request such as SIGINT or SIGTERM where supported.

### 13. What should an application do after handling a shutdown signal?

- A. Stop new work, clean up resources, and let the event loop finish
- B. Call process.exit() before cleanup begins
- C. Ignore open resources
- D. Start an unlimited interval

**Answer: A.**

**Explanation:** Orderly shutdown gives in-flight work and output a chance to complete. Use process.exitCode when setting an exit status without forcing immediate termination.

### 14. Are process signals available inside Worker threads?

- A. No
- B. Yes, all signals are delivered to every Worker
- C. Only SIGINT is available
- D. Only when using EventEmitter

**Answer: A.**

**Explanation:** Node.js process signal events are not available on Worker threads.

## Short-answer questions

### 15. What does emit() do to listeners attached to an EventEmitter?

**Answer:** It invokes the listeners for that event synchronously in registration order and passes along any supplied arguments.

**Explanation:** The listener may schedule asynchronous work, but the call to emit() itself is synchronous.

### 16. Why is once() useful for a ready event?

**Answer:** The handler is removed automatically after the first ready event.

**Explanation:** This avoids accidentally running initialization code multiple times if ready is emitted again.

### 17. What does events.once(emitter, name) return?

**Answer:** A Promise that resolves to an array containing the event's arguments when that event is emitted.

**Explanation:** It rejects if the emitter emits error while the Promise is waiting for another event. Install the listener before starting work that may emit.

### 18. Why can sequentially awaiting two event names miss an event?

**Answer:** The emitter might emit both events synchronously before the code resumes from the first await and registers the second listener.

**Explanation:** Register listeners for all events before starting the operation, or consume events through a suitable async iterator.

### 19. Why should an asynchronous EventEmitter listener catch its own failures?

**Answer:** EventEmitter does not automatically wait for the listener's Promise, so a rejection may otherwise become unhandled.

**Explanation:** Handle the rejection in the listener or configure captureRejections with an explicit error policy.

### 20. What is the difference between setTimeout() and setImmediate() at a high level?

**Answer:** setTimeout() waits until its timer threshold is eligible and the event loop can run it. setImmediate() schedules work for the check phase after poll processing.

**Explanation:** Their relative order depends on context. From an I/O callback, setImmediate() runs before a zero-delay timer scheduled in that callback.

### 21. Why can long synchronous work delay an already eligible timer?

**Answer:** The main JavaScript thread cannot run another callback while the synchronous function is still executing.

**Explanation:** A timer becoming eligible does not interrupt current JavaScript. Break up CPU-heavy work or move suitable work to worker threads.

### 22. What does unref() change about a Timeout?

**Answer:** It tells Node.js that this timer alone should not keep the event loop alive.

**Explanation:** The process can exit before the timer fires if no other active work remains.

### 23. Why should shutdown logic be idempotent?

**Answer:** Multiple shutdown requests can arrive, and cleanup should not run destructively more than once.

**Explanation:** A simple boolean guard can prevent duplicate close or cleanup operations.

### 24. Why is immediately calling process.exit() from a signal handler often a poor choice?

**Answer:** It can stop pending cleanup and truncate output before it is flushed.

**Explanation:** Stop active work, close resources, set process.exitCode if needed, and let the event loop finish.

## Scenarios

### 25. An EventEmitter listener starts a Promise and then emit() returns before that Promise finishes. Is this expected?

**Answer:** Yes.

**Explanation:** EventEmitter calls the listener synchronously, but it does not await the Promise returned by an async listener.

### 26. A program logs that its setTimeout(..., 100) callback ran after 140 milliseconds. Does that prove the timer is broken?

**Answer:** No.

**Explanation:** The delay is a threshold, and callbacks can run later if JavaScript is busy or the event loop and operating system are handling other work.

### 27. A recursive process.nextTick() loop runs while file I/O is pending. What might happen?

**Answer:** The nextTick queue may keep running and starve the event loop from processing the I/O callback.

**Explanation:** Use a deliberate yielding strategy such as setImmediate() when other event-loop work should get a chance to run.

### 28. A Promise listener is registered after a request starts. The request can complete immediately, so sometimes the program waits forever. What is the fix?

**Answer:** Create the events.once() Promise before starting the request.

**Explanation:** Event listeners only receive events emitted after they are registered.

### 29. A service adds an async error listener but does not catch errors inside it. What is the risk?

**Answer:** The async listener can reject, and the rejection may not be handled by EventEmitter automatically.

**Explanation:** Catch errors inside the listener or deliberately configure rejection capture and its error handler.

### 30. A program adds a SIGTERM handler on Windows and expects the operating system to deliver SIGTERM just as on Linux. Is that portable?

**Answer:** No.

**Explanation:** Real signal support differs by platform. Node.js documents SIGTERM as unsupported on Windows, even though an event listener for that name can be installed.

### 31. An application calls timer.unref() and then the process exits before a reminder is printed. Why?

**Answer:** The unref'ed timer was the only thing that would have kept the event loop alive.

**Explanation:** unref() means the process is allowed to exit without waiting for that timer.

### 32. Two listeners are registered for a custom event. The second listener sees a value changed by the first listener. Why?

**Answer:** Listeners run synchronously in registration order, so the first listener's change is visible to the second.

**Explanation:** Keep event listeners predictable and avoid hidden shared-state dependencies where possible.

## Coding questions

### 33. Create an EventEmitter with one repeating listener and one one-time listener.

**Answer:**

~~~js
import { EventEmitter } from "node:events";

const bus = new EventEmitter();

bus.on("update", (value) => {
  console.log("Every update:", value);
});

bus.once("ready", () => {
  console.log("Ready was handled once");
});

bus.emit("update", 1);
bus.emit("ready");
bus.emit("ready");
~~~

**Explanation:** on() remains registered, while once() removes itself after the first matching emission.

### 34. Wait for a completion event and read its first argument.

**Answer:**

~~~js
import { EventEmitter, once } from "node:events";

const bus = new EventEmitter();
const completion = once(bus, "complete");

setTimeout(() => {
  bus.emit("complete", { ok: true });
}, 10);

const [result] = await completion;
console.log(result.ok);
~~~

**Explanation:** The Promise listener is installed before the timer starts the event. The event arguments are returned as an array.

### 35. Handle an EventEmitter error event.

**Answer:**

~~~js
import { EventEmitter } from "node:events";

const bus = new EventEmitter();

bus.on("error", (error) => {
  console.error("Operation failed:", error.message);
});

bus.emit("error", new Error("Disk unavailable"));
~~~

**Explanation:** Without an error listener, emitting error throws.

### 36. Cancel a Promise-based timer with an AbortController.

**Answer:**

~~~js
import { setTimeout as delay } from "node:timers/promises";

const controller = new AbortController();
const pending = delay(5000, "finished", {
  signal: controller.signal
});

controller.abort();

try {
  await pending;
} catch (error) {
  if (error.name === "AbortError") {
    console.log("Timer cancelled");
  } else {
    throw error;
  }
}
~~~

**Explanation:** Cancelling a Promise-based timer rejects its Promise with an AbortError.

### 37. Stop a repeating timer when SIGINT is received.

**Answer:**

~~~js
import process from "node:process";

const heartbeat = setInterval(() => {
  console.log("Still running");
}, 1000);

process.once("SIGINT", () => {
  clearInterval(heartbeat);
  process.exitCode = 0;
  console.log("Stopped cleanly");
});
~~~

**Explanation:** The handler clears the active timer and lets Node.js exit naturally after the callback finishes. A real service should also close its servers, streams, and other resources.

### 38. Use setImmediate() to schedule a later callback without assuming its ordering against a top-level zero-delay timer.

**Answer:**

~~~js
console.log("Before scheduling");

setImmediate(() => {
  console.log("Immediate callback");
});

setTimeout(() => {
  console.log("Timer callback");
}, 0);

console.log("After scheduling");
~~~

**Explanation:** The first and last messages are synchronous and have a guaranteed order. The order of the immediate and zero-delay timer at top level is not guaranteed.
