# 120 - Web Crypto and secure random values

JavaScript offers more than one way to produce a value that looks random. A visual effect or casual game may only need a non-predictable sequence for presentation. A security token, challenge, or cryptographic operation needs a cryptographically secure source.

Use the browser's Web Crypto API for cryptographic randomness. Use its key-generation methods for cryptographic keys. Do not build your own cryptographic algorithms.

## Learning goals

After this lesson, you should be able to:

- distinguish ordinary pseudo-random values from cryptographically secure random values;
- use crypto.getRandomValues() to fill integer typed arrays;
- convert random bytes into a readable token representation;
- avoid modulo bias when choosing a random integer from a range;
- use crypto.randomUUID() for identifiers without treating an ID as authorization;
- distinguish hashing, encryption, and key generation;
- use SubtleCrypto for a supported operation without implementing cryptography yourself;
- recognize secure-context requirements and browser limitations.

## Ordinary randomness and cryptographic randomness

Math.random() returns a pseudo-random floating-point number from zero inclusive to one exclusive. It is suitable for many non-security tasks, such as selecting a decorative animation delay or shuffling sample data for a demo.

Do not use Math.random() for:

- session or password-reset tokens;
- authentication challenges or one-time codes;
- cryptographic keys or nonces;
- lottery, betting, or other values where users can gain from predicting or influencing the result;
- security-sensitive identifiers.

The output of Math.random() is not intended to resist an attacker trying to predict it. Scaling it into a large integer or calling it many times does not make it cryptographically secure.

## Generate cryptographically secure bytes

Use crypto.getRandomValues() with an integer typed array:

~~~js
const bytes = new Uint8Array(16);
crypto.getRandomValues(bytes);

console.log(bytes);
~~~

The browser fills the array in place. For example, a Uint8Array stores one byte in each entry, so an array of 16 entries holds 16 random bytes.

The method supports integer typed arrays, not floating-point typed arrays. A single call cannot request more than 65,536 bytes. Make smaller calls if a larger amount is genuinely needed.

The browser uses a cryptographically secure pseudorandom generator seeded with platform entropy. The API is synchronous. It is not a request for user permission and it does not make an application's storage or authentication design secure by itself.

### Convert bytes into hexadecimal text

A byte can be displayed as two hexadecimal characters. The following function converts a byte array without changing the bytes:

~~~js
function bytesToHex(bytes) {
  return Array.from(bytes, (byte) =>
    byte.toString(16).padStart(2, "0")
  ).join("");
}

const tokenBytes = new Uint8Array(32);
crypto.getRandomValues(tokenBytes);

const tokenText = bytesToHex(tokenBytes);
console.log(tokenText);
~~~

Thirty-two random bytes contain 256 bits of random material and produce 64 hexadecimal characters. The output is an encoding of the bytes, not an encryption of them.

A hexadecimal string is convenient to inspect and copy. Other encodings such as base64url can be more compact, but their alphabet and padding rules need careful handling.

### Keep client-side secrets in perspective

Anything generated in browser JavaScript is available to that page and to its developer tools. A value generated by a public client is not a secret from the person using that client.

For example, creating a random value in a browser does not make it a safe session token for a server. Authentication and recovery tokens should be generated, validated, expired, and protected by the server as part of a complete design. Do not put tokens into URLs, logs, or analytics events.

## Choose a random integer without bias

A common shortcut is to generate a random 32-bit integer and take its remainder:

~~~js
const values = new Uint32Array(1);
crypto.getRandomValues(values);

const result = values[0] % 6;
~~~

This can make some results slightly more likely than others because 2 to the 32nd power is not always divisible by the range size. This difference is called modulo bias.

For a small range, reject the values above the largest evenly divisible portion:

~~~js
function secureRandomInt(maxExclusive) {
  const range = 2 ** 32;

  if (
    !Number.isSafeInteger(maxExclusive) ||
    maxExclusive < 1 ||
    maxExclusive > range
  ) {
    throw new RangeError("maxExclusive must be an integer from 1 to 2^32.");
  }

  const limit = Math.floor(range / maxExclusive) * maxExclusive;
  const sample = new Uint32Array(1);

  do {
    crypto.getRandomValues(sample);
  } while (sample[0] >= limit);

  return sample[0] % maxExclusive;
}

const dieResult = secureRandomInt(6) + 1;
console.log(dieResult);
~~~

The function returns an integer from zero inclusive up to maxExclusive exclusive. Adding one makes the dice result range from one through six.

Rejection sampling discards only the values that would give some outcomes an extra representation. For casual non-security visuals, the simpler Math.random() approach is usually enough. For security-sensitive choices, use a well-reviewed implementation and a clear threat model.

## Generate UUIDs for identifiers

On a secure context, crypto.randomUUID() returns a version 4 UUID:

~~~js
const recordId = crypto.randomUUID();
console.log(recordId);
~~~

A UUID is useful as a practical identifier for a record or request. It does not prove who a user is, grant permission, or guarantee a globally unique value in every possible system. Authorization must be checked independently.

randomUUID() and getRandomValues() serve different needs:

| API | Useful for |
| --- | --- |
| crypto.randomUUID() | A standard UUID string for an identifier |
| crypto.getRandomValues() | A byte sequence for a token or another format you define |

Do not create a custom UUID by guessing at its bit layout when the built-in method is available.

## Web Crypto operations with SubtleCrypto

crypto.subtle provides low-level cryptographic operations such as hashing, signing, verification, encryption, decryption, key import, and key generation. Its operations are asynchronous and the API is available only in secure contexts such as HTTPS pages and localhost development.

### Hashing is not encryption

A digest is a one-way result for input data. It does not hide the input and is not a key.

~~~js
async function sha256Hex(message) {
  const input = new TextEncoder().encode(message);
  const digest = await crypto.subtle.digest("SHA-256", input);
  return bytesToHex(new Uint8Array(digest));
}

const fingerprint = await sha256Hex("sample message");
console.log(fingerprint);
~~~

A digest can help compare data or create a content fingerprint. It cannot be decrypted to recover the original message. A plain fast digest such as SHA-256 is not suitable for storing passwords. Password storage needs a purpose-built, slow password-hashing design on the server.

### Generate keys with the key API

Do not use getRandomValues() to assemble cryptographic keys yourself. Use the API's key-generation operation for the algorithm and usages that the application needs:

~~~js
async function createAesKey() {
  return crypto.subtle.generateKey(
    { name: "AES-GCM", length: 256 },
    false,
    ["encrypt", "decrypt"]
  );
}
~~~

Here, false requests a non-extractable key. The returned CryptoKey can be passed to compatible Web Crypto methods, but the raw key material cannot be exported with the normal exportKey operation.

This snippet only demonstrates key creation. It is not a complete encryption design. Real encryption also needs correct nonce generation and uniqueness, authenticated data decisions, key lifecycle, storage, and protocol design. Use an established protocol or a security-reviewed library when building a product.

## Secure contexts and feature detection

SubtleCrypto and randomUUID are marked for secure contexts. Serve deployed applications over HTTPS. Localhost is treated as a secure context for development by modern browsers.

getRandomValues() is a special case in the Web Crypto interface and can be available outside a secure context. Still deploy security-sensitive applications over HTTPS and check that the methods your feature needs exist:

~~~js
function canUseRandomUuid() {
  return typeof crypto !== "undefined" &&
    typeof crypto.randomUUID === "function";
}

function canUseSubtleCrypto() {
  return typeof crypto !== "undefined" &&
    Boolean(crypto.subtle);
}
~~~

Feature detection tells you whether an API is exposed. It does not prove that an entire security design is correct.

## Common mistakes

- Using Math.random() for tokens, keys, passwords, or security challenges.
- Assuming a value becomes secure because it is long or generated many times.
- Using modulo on random integers when each outcome must be equally likely.
- Asking getRandomValues() for more than 65,536 bytes in one call.
- Passing a floating-point typed array to getRandomValues().
- Generating a key by copying random bytes into a custom format.
- Treating a UUID as a password or authorization check.
- Confusing a digest with encryption.
- Using a fast digest to store user passwords.
- Assuming client-generated values are secret from the client.
- Putting tokens into URLs or logs.
- Writing custom encryption, signing, or key derivation algorithms.
- Assuming secure randomness fixes insecure token storage or missing server authorization.

## Key points

- Math.random() is for non-security randomness. Use Web Crypto when unpredictability matters for security.
- getRandomValues() fills an integer typed array with cryptographically secure random values.
- One getRandomValues() call is limited to 65,536 bytes.
- Rejection sampling avoids modulo bias for bounded integers.
- randomUUID() provides a UUID identifier, not an authorization decision.
- Use SubtleCrypto key generation methods for keys and established algorithms for cryptographic operations.
- Hashing, encryption, and random generation are different operations.
- Client-side code cannot keep a value secret from the user running it.
- Use HTTPS and handle API support and errors deliberately.
